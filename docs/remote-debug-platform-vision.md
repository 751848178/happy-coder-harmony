# Happy Coder 远程调试平台愿景

> 状态：Draft
> 日期：2026-03-13
> 适用范围：Happy Coder Flutter 客户端及后续远程调试体系

## 1. 背景

当前 Happy Coder 已经具备“远程开发/远程继续会话”的基础能力，但这条链路主要解决的是：

- 远程接入同一个编码会话
- 远程查看会话消息、工具调用和终端状态
- 在移动端或其他设备上继续推进开发任务

它尚未完整解决以下核心问题：

- 无法远程直接看到应用运行效果
- 无法远程观察页面变化、崩溃现场和交互结果
- 无法统一接入 Flutter、Web、原生 App 的调试器能力
- 无法把“会话控制”扩展为“预览 + 调试 + 控制”的完整闭环

因此，项目下一阶段的方向不是单纯复制 GitHub Happy，而是基于现有 Happy Coder 的会话基础设施，演进为一个支持远程预览与远程调试的平台。

## 2. 愿景

将 Happy Coder 从“远程开发会话客户端”扩展为“统一远程调试控制台”。

目标不是只支持某一个框架，而是支持调试多类产品：

- Flutter 应用
- Web 应用
- 原生 App（Android / iOS / HarmonyOS）

这里所说的“支持这些技术栈”，指的是支持调试这些技术栈开发出来的产品，而不是要求平台本身必须使用这些技术栈实现。

## 3. 核心判断

### 3.1 这个方向需要后端支持

如果只是个人临时调试单机，可以靠 `ssh`、端口转发、Tailscale、`flutter attach` 等方式完成。

但如果要把它做成产品能力，后端是必需的，至少要负责：

- 用户鉴权与设备授权
- 设备注册、在线状态、控制权切换
- 调试会话创建、回收和审计
- 日志、事件、截图、视频流的转发
- 调试协议代理
- WebRTC 信令与必要的中继能力

### 3.2 不建议完全重写，也不建议把所有东西硬塞进现有 Happy 后端

推荐方向：

- 客户端基于现有 `happy-coder-flutter` 继续二开
- 远程调试后端单独新开项目
- 被调试机器侧新增独立 `agent/runner`

这是因为现有 Happy 的强项是“会话控制”，而远程调试新增的是另一类问题：

- 运行时编排
- 调试器接入
- 媒体流与画面预览
- 输入回放与远程控制

它们和普通聊天、消息同步、工具调用不属于同一复杂度层级。

## 4. 产品边界

### 4.1 第一阶段优先支持 Flutter

Flutter 最适合作为第一落地方向，因为其调试链路相对统一：

- `flutter run --machine`
- `flutter attach`
- Dart VM Service
- DevTools
- 热重载/热重启
- Widget 异常与运行日志

### 4.2 平台设计必须从一开始就支持扩展到 Web 和原生 App

平台底座应该是通用的，具体能力通过不同 adapter 接入：

- Flutter adapter
- Web adapter
- Native adapter

这样未来扩到 Web 与原生 App 时，不需要推翻整体架构。

### 4.3 第一版不是“全能力 IDE 替代品”

第一版优先解决三个痛点：

- 看不到效果
- 拿不到调试上下文
- 无法从远端快速确认修改是否生效

第一版不追求一次性实现所有平台的源码级断点调试。

## 5. 目标能力模型

平台能力拆分为两层。

### 5.1 通用控制底座

所有技术栈共享：

- 设备注册与身份绑定
- 调试会话管理
- 权限审批与控制权切换
- 日志/事件流统一传输
- 截图、预览、录屏、视频流
- 输入事件转发
- 远端环境状态检测

### 5.2 运行时适配器

不同技术栈接不同调试协议：

#### Flutter

- `flutter run --machine`
- `flutter attach`
- Dart VM Service 代理
- DevTools 入口代理
- Hot Reload / Hot Restart
- Frame 截图或预览流

#### Web

- Chrome DevTools Protocol
- Console / Network / Performance / Error 采集
- 页面截图与实时预览
- 自动刷新与页面控制
- Playwright 级别的自动交互能力

#### 原生 App

- 安装、启动、停止、重启
- 系统日志采集
- 截图与录屏
- 输入注入
- 深层原生断点调试后置

## 6. 推荐架构

### 6.1 Client

基于现有 `happy-coder-flutter` 二开，承担：

- 调试会话入口
- 设备列表与状态展示
- 权限审批 UI
- 远程预览画面
- 日志面板
- 基础调试操作入口

### 6.2 Debug Control Backend

单独新建服务，承担：

- 用户与设备鉴权
- 调试会话调度
- 调试通道代理
- WebSocket / Socket.IO 事件聚合
- WebRTC 信令
- 审计与权限控制

### 6.3 Remote Agent / Runner

部署在被调试机器上，承担：

- 启动和管理目标应用
- 接入调试协议
- 上报日志、状态和截图
- 建立视频流或截图流
- 接收远程控制指令

### 6.4 Runtime Adapters

按技术栈拆分：

- Flutter Runner Adapter
- Web Runner Adapter
- Native Runner Adapter

## 7. 与 Happy 现有体系的关系

### 7.1 可以复用的部分

- 用户与设备概念
- 会话概念
- Socket 实时连接能力
- 权限审批交互模型
- 移动端控制台 UI
- 现有 Flutter/Harmony 客户端工程基础

### 7.2 必须新增的部分

- 调试会话域模型
- 调试协议代理层
- 远程预览链路
- 视频流/截图流链路
- 被调试机器侧 agent
- 多技术栈 adapter

### 7.3 结论

方向上应当“客户端二开 + 后端新开 + agent 新开”，而不是单纯 fork 上游 Happy 后直接堆功能。

## 8. 分阶段落地路线

### 阶段 1：Flutter MVP

目标：先解决“远程看效果”和“基础调试可达”。

范围：

- 启动 Flutter 应用
- 采集运行日志和错误
- 回传周期性截图
- 支持 `flutter attach`
- 代理 Dart VM Service / DevTools
- 支持 Hot Reload / Restart 的远程触发

输出结果：

- 用户能在 Happy Coder 中远程看到 Flutter 应用效果
- 用户能远程查看日志、异常与基本调试状态

### 阶段 2：增强 Flutter + Web MVP

目标：把“远程看效果”提升为“远程调试闭环”。

范围：

- Flutter 更稳定的预览流
- Web 调试接入 CDP
- 页面截图和 console/network/error 面板
- 基础交互控制

### 阶段 3：实时流与原生 App 支持

目标：把平台扩展为多运行时远程调试平台。

范围：

- WebRTC 视频流
- 输入事件回放
- Android / HarmonyOS 设备调试接入
- 控制权切换和审计完善

## 9. 非目标

以下内容不属于第一阶段目标：

- 一次性支持所有平台的完整断点调试
- 完整替代本地 IDE
- 一开始就做重型远程桌面产品
- 把 Happy 会话系统和远程调试系统彻底耦合成单体

## 10. 成功标准

当以下条件成立时，说明该方向成立：

- 用户可以在远端看到应用运行结果
- 用户可以拿到日志、错误和运行状态
- 用户可以远程触发基本调试操作
- 平台可以在不推翻架构的前提下扩展到 Web 与原生 App
- 客户端、后端、agent 的职责边界清晰

## 11. 当前决策

截至当前，项目方向明确如下：

1. 以 Flutter 远程调试作为第一落地点。
2. 平台目标不是只做 Flutter，而是面向 Flutter / Web / 原生 App 的统一远程调试底座。
3. 必须建设后端与远端 agent，不能只靠客户端补功能。
4. 继续复用 `happy-coder-flutter` 作为控制端，而不是从零重写客户端。
5. 远程调试后端应独立新建，不直接把全部能力塞进现有 Happy 会话后端。
