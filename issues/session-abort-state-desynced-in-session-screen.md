# 会话页手动停止后状态不同步问题记录

## 背景

本次问题的表象是：

- 用户在移动端点击“停止当前回复”后，PC 端实际上已经停止。
- 但当前会话页里的输入框提示、发送按钮、停止按钮等状态没有立即恢复。
- 只有先返回会话列表，再重新进入会话页，状态才会看起来正常。

这会造成明显的状态错乱感，让用户误以为“停止没有生效”。

## 根因定位

### 1. 当前会话页有一个本地活跃响应标记 `_activeResponseLocalId`

- 发送消息时，会话页会把当前请求的本地 `localId` 写入 `_activeResponseLocalId`。
- 输入区是否忙碌、停止按钮是否显示，都会把这个本地标记算进去。

这本来是为了在远端消息还没完全回来前，先维持正确的“正在回复”状态。

### 2. 现有释放条件只覆盖“正常完成”路径，没有覆盖“停止后无输出”路径

- `_reconcileQueuedMessageState()` 里，释放 `_activeResponseLocalId` 依赖 `sessionActiveResponseHasCompleted(...)`。
- 这套判定要求满足以下条件之一：
  - 收到明确 completion 信号，如 `turn_aborted / ready / stop / turn-close`
  - 或者已经有可渲染的 agent 输出

问题在于：

- 手动停止后，如果这一轮没有最终文本输出，
- 且停止完成信号还没及时进入当前消息快照，
- `_activeResponseLocalId` 就会一直残留在当前会话页里。

结果就是当前页会持续把自己当成“仍在回复中”。

### 3. `abortSession()` 只等待了消息刷新，没有等待会话态刷新完成

- 停止 RPC 成功后，原实现只 `await loadSessionMessages(sessionId)`。
- `loadSessions(force: true)` 是 `unawaited(...)` 后台执行。

这会让当前页在停止动作完成的这一拍里，拿不到最新的 `session.thinking == false`，从而更难及时判断“远端已经真正停止”。

### 4. 返回列表再进入会话，会意外掩盖这个问题

- 会话页是 StatefulWidget。
- 返回列表再重新进入时，本地 `_activeResponseLocalId` 会被重置。

因此表象上像是“重新进入后状态好了”，但真实原因是旧页面里的本地状态没有被及时释放。

## 修复方案

### A. 停止 RPC 后同步等待最新消息和最新会话态

- `abortSession()` 改成同时等待：
  - 最新消息快照
  - 最新会话快照

这样当前页在停止完成后能尽快拿到远端的真实 busy/thinking 状态。

### B. 新增“停止后远端已空闲”的专用判定

- 新增 `sessionAbortHasSettledRemotely(...)`。
- 在“停止请求已成功发出”的上下文里：
  - 优先相信最新远端会话态 `session.thinking`
  - 不再被历史 thinking 文本或旧工具消息长期卡住

这条判定只用于“释放停止后的本地活跃标记”，不改变普通回复流程的完成语义。

### C. 当前页在远端已停止后主动释放本地残留状态

- 当观察到远端已停止后，会话页会同步清理：
  - `_activeResponseLocalId`
  - `_manualThinkingOverride`
  - `_awaitingAbortRemoteSettle`

这样输入框提示、发送按钮、停止按钮都会在当前页直接恢复，不再依赖重新进入页面。

### D. UI 推导改用“有效活跃响应标记”

- 当前页不再机械地把 `_activeResponseLocalId != null` 当成仍在回复。
- 如果已经确认“停止后远端已空闲”，就会把这个本地标记视为失效。

这样即使本地清理动作还在同一帧之后执行，按钮状态也能先一步正确更新。

## 测试与验证

- 新增停止后远端空闲判定的单元测试，覆盖：
  - 停止后即使没有最终文本输出，也能识别远端已停止
  - 远端仍在 thinking 时不会误判为已停止

## 后续开发约束

- 任何“本地 optimistic / in-flight 标记”都必须有对应的“远端已完成 / 已停止”释放路径。
- 不允许把“正常完成”和“手动停止完成”共用一套过于狭窄的释放条件，否则极易出现当前页状态卡住的问题。
- 对于会话页这种 StatefulWidget，必须特别检查“重新进入页面后恢复正常”的现象，因为这通常意味着本地状态释放链路有缺口，而不是真正已经修好。
