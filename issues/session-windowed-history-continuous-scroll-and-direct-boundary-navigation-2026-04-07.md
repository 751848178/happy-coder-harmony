# 会话消息窗口化后仍需保持连续可访问与边界直达

## 背景

为解决大会话进入详情页时的内存暴涨和首屏卡顿，我们把消息列表改成了“常驻内存窗口 + 本地归档”的模式。这个方向是正确的，但随后暴露出两个新问题：

1. 用户点击“到顶 / 到底”时，页面会卡住或者长时间无响应。
2. 页面出现“后台准备完整消息...”之类的实现细节提示，体验上等同于告诉用户“现在还不能正常访问全部消息”。

目标应该是：

- 所有消息都可以被连续访问。
- 屏幕内只渲染当前视口附近的数据。
- 内存里只保留受控窗口，而不是把全量消息常驻 Dart 堆。
- 用户不需要理解“归档”“窗口”等内部实现。

## 根因

### 1. 边界跳转实现成了循环跨窗口推进

之前“到顶 / 到底”的实现会在 UI 行为里循环调用“加载更早窗口 / 更新列表 / 再滚动”的链路，直到抵达历史边界。对于大消息量会话，这相当于把很多次窗口切换串成一次同步跳转，导致：

- 多次 Hive 读取
- 多次列表重建
- 多次滚动位置修正
- 按钮看起来像“点了没反应”

### 2. 归档读取仍有 O(n) 扫描

本地归档虽然已经从内存转移到了 Hive，但按范围读取仍然依赖扫描会话全部归档 key 并排序。随着归档条数增大，每次窗口切换都会放大读取成本。

### 3. UI 暴露了内部状态机

“后台准备完整消息...”这种提示，本质上是把内部的 archive hydration 状态直接暴露给用户。对用户来说，他们只关心能不能顺滑地滚到任何一条消息，而不是知道内部用了什么同步策略。

### 4. 边界按钮状态只看当前窗口

“到顶 / 到底”按钮是否可用，之前主要依据当前 `ScrollPosition`。当当前窗口已到顶，但归档里仍有更早消息时，按钮状态和真实能力并不一致。

## 修复策略

### 1. “到顶 / 到底”改为一次性装载目标边界窗口

不再循环跨窗口推进，而是：

- 到顶：直接装载最早窗口，再滚到该窗口顶部。
- 到底：直接装载最新窗口，再滚到列表底部。

这样把原来的多次窗口切换压缩成一次窗口装载 + 一次滚动恢复。

### 2. 归档存储增加 summary 元数据

为每个会话保存归档摘要：

- `messageCount`
- `isComplete`

并将归档 key 改为可直接按索引访问的形式，使范围读取退化为 O(limit)，而不是 O(total archived messages)。

### 3. 连续滚动仍保持按边缘续窗

用户手势滚动到顶部/底部附近时，仍然只续一段相邻窗口，不做全量装载。这样：

- 正常阅读路径保持平滑
- 内存驻留仍然受控
- 不需要把全部消息一次性恢复到内存

### 4. 移除实现细节提示

详情页不再展示“后台准备完整消息...”之类的提示。全量历史访问能力应该通过真实交互来体现，而不是通过横幅解释。

## 落地结果

本次改动后，消息历史链路遵循以下约束：

- 全量消息保存在本地 archive，可被连续访问。
- 当前内存只保留 resident window。
- 正常滚动按边缘逐窗续接。
- “到顶 / 到底”直接装载边界窗口，不再循环跨窗。
- 归档范围读取为 O(limit)。

## 后续建议

1. 为“跨窗口连续滚动”和“到顶 / 到底直达边界”补充 widget / integration test。
2. 对超大 markdown / tool 输出继续做懒解析和结果缓存，避免单条消息内容成为新的热点。
3. 如果后续仍发现 Hive 读取在极大会话上成为瓶颈，可以进一步引入会话级页索引，而不是仅依赖顺序 key。
